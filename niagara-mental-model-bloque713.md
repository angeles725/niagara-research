## 713.1 — `META-INF/module.xml` — the manifest (read at boot)

[CERT] The station daemon reads this at boot (`DefaultModulesFileManager`, [Block 630]). Key attributes:
- **`runtimeProfile`** = `rt` | `ux` | `wb` | `se` — LOAD-BEARING: a missing attribute → the jar is silently not
  loaded; `-wb` is invisible to a headless daemon. It is the attribute, not the filename ([Block 630] §630.2-6).
- **`moduleName`**, **`vendor`** (e.g. `ANGELES`, [Block 638]), **`vendorVersion`** (bump per release).
- **`<dependency>`** entries — other modules this part needs (declare real deps; reference shared libs rather than
  shading them).
- **`<permissions>`** — declare ONLY if used; the base grant covers a normal module; delete the empty
  New-Module-Wizard scaffold ([Block 635]).
- It is generated by the `niagara-module` plugin from the gradle config — you set these via the build, not by
  hand-editing the jar.

## 713.2 — `module-include.xml` — the `<type>` registry (build INPUT)

[CERT] The list of exported types Slotomatic reads (WF2 / [Block 631]). One `<type>` per component:
```xml
<type name="MyThing" class="com.shop.mymod.BMyThing"/>
```
Attributes: `name`, `class` (+ optional `ordScheme`, child `<agent>`/`<on>` for view/agent registration,
`<file>`/`<ext>` for file-type handlers). `abstract`/`final`/`modifiers` are NOT here — they come from bytecode
at registry build. A class absent from `<type>` is not a type (WF2 guard). Scaffolded by the wizard or authored
by hand; it is an INPUT, not generated.

## 713.3 — `module.palette` — the drag-and-drop BOG (optional, recommended)

[CERT] A BOG file at the jar root that makes your components drag-and-drop in Workbench. It is **ungated** (no
license/permission check), **lazy-decoded** once at first nav expansion, and **fault-tolerant** (missing types
skipped, not a boot error) ([Block 634] §634.2-4). Ship one for any module exporting reusable `BComponent` types
(zero code, zero permission, zero license cost). Chihuahua exports 6+ components but ships none — a free
improvement ([Block 636] #4).

## 713.4 — `module.lexicon` — localization

[INFER] The lexicon files (`lexicon/<locale>.lexicon`) hold the display/message strings keyed by lexicon key
(e.g. `driver:pingFail` seen in the alarm records, [Block 702]). UI/alarm text should reference a lexicon key,
not a hardcoded string, so the module is localizable. (Present even in empty scaffold jars like `interfaz1-wb`,
[Block 642].)

## 713.5 — The author's file map

[INFER]

| File | Where | What goes in it | Authored how |
|---|---|---|---|
| `META-INF/module.xml` | jar root | runtimeProfile, name, vendor, version, deps, permissions | via gradle config (niagara-module) |
| `module-include.xml` | part root | `<type>` per exported component | wizard/hand (INPUT to Slotomatic) |
| `module.palette` | jar root | BOG of components for drag-and-drop | hand-authored BOG (optional) |
| `lexicon/*.lexicon` | jar | display/message strings by key | hand |
| `<Class>.java` (AUTO region) | src | slot constants/getters/TYPE | Slotomatic (never hand-edit inside markers) |
