## 712.1 — The round-trip in five stages

[CERT] From the annotation you write to a runtime-resolvable `moduleName:typeName` ([Block 631] §631.1):

1. **BUILD input** — you write `@NiagaraType` on the class + one `<type name= class=>` in `module-include.xml`.
   Slotomatic READS `module-include.xml` (`Slotomatic.java:140`) + parses `@Niagara*` via `NiagaraTypeProcessor`
   (JavaParser source model) and WRITES the AUTO slot region into your `.java` (`Compiler.write`, `:296-301`).
2. **RegistryDatabase** — at registry build the `<type>` becomes an `NTypeInfo` (structural — name, class-name
   string, flags from bytecode — NO `Class` object yet).
3. **NModule.types** — the module holds the type as a className STRING, lazily.
4. **Resolve** — `Registry.getType` / `BTypeSpec.resolve("moduleName:typeName")` returns the `NTypeInfo`.
5. **Load once** — `NModule.loadClass` loads the `Class` exactly once via the `ModuleClassLoader`; the static
   `TYPE = Sys.loadType(BFoo.class)` runs, `NType` self-registers, and the map entry is promoted String → Type.

So the type is loaded LAZILY, once, on first resolve — not at boot.

## 712.2 — What Slotomatic writes (the AUTO region)

[CERT+INFER] Between `/*+ BEGIN BAJA AUTO GENERATED +*/ … /*+ END … +*/`, Slotomatic generates: the property/
action slot CONSTANTS (`public static final Property foo = newProperty(...)`), the typed getters/setters
(`getFoo()`/`setFoo()`), the action invoke stubs, and the closing `public static final Type TYPE =
Sys.loadType(BFoo.class)`. The region carries a **hash** of the source model; if you add a `@Niagara*` slot and
do NOT re-run Slotomatic, the hash + constants go stale → compile errors or missing slots at runtime (the
`AWAITING SLOTOMATIC REGEN` state on chihuahua's `BChiUp`, [Block 650]).

**You never edit inside the AUTO markers by hand** — Slotomatic owns that region; your code goes outside it.

## 712.3 — The guard, and the correction it implies

[CERT] `Compiler` refuses to generate for a class not in the manifest:
`Cannot update <file>; it is not in module-include.xml` (`Compiler.java:270`). So `module-include.xml` is the
**driving registry** — the single source of "which classes are types." This corrects [Block 12]'s claim that
the file is "auto-generated by an annotation processor": it is a **hand-/wizard-authored INPUT**, READ (not
written) by Slotomatic, which is categorically not a JSR-269 processor ([Block 631] §631.2, §14).

## 712.4 — Dev implication (the round-trip rule)

[INFER] The practical loop this creates:
- Add/change a component type or slot → edit the `@Niagara*` annotation → **add the `<type>` to
  `module-include.xml` if it's a new type** → run `:slotomatic` → the AUTO region regenerates → compile.
- Rename/remove a type → update `module-include.xml` too, or the registry keeps the stale entry.
- A class you forgot to list in `<type>` is dead bytecode: no slots generated, `BTypeSpec.resolve` never finds
  it, and no error points at the omission — the class simply isn't a type.
