## 822.1 — The constraint: the existing `setpoint` is not writable over oBIX `[CERT — full detail in B823]`
`BRoomPanel.setpoint` is a `BStatusNumeric` (`= BStatusValue = BStruct = BComplex`, NOT `BSimple`). Two [CERT] facts make a plain oBIX PUT fail (detail + the no-code verdict = [B823]):
- **Never advertised writable**: the oBIX encoder sets `writable="true"` ONLY for a `BSimple` value under `canWrite` (`ObixUtils.encode:241-243`), and `BStatusValueAgent.processAttr:51-53` + `BControlPointAgent.processAttr:60` strip the `writable` attribute for any `StatusValue`/`ControlPoint`. So a client never sees the slot as writable.
- **"Cannot translate"**: a bare `<real val="21.5"/>` PUT decodes against the `BStatusNumeric` prototype; because it is `BComplex` (not `BSimple`), `ObixDecoder.decode2` hits the `!isSimple()` branch and throws `IllegalStateException("Cannot translate")` (`ObixDecoder.java:346`, twin at `:197`) BEFORE any `parent.set()`. Nothing in the corpus implements `BIObixWritable` (the only interface `ObixUtils.serviceWrite:536` would honor), so the property-PUT path is functionally closed for a `BStatusNumeric`. (A hand-built `<obj is="baja:StatusNumeric"><real name="value" val=".."/></obj>` could reach `parent.set` via the `<obj>`-children branch `:200-216` + `setFromVal:569`, but is non-standard and unadvertised — [B823] settles whether it writes live.)

**So a remote setpoint needs a WRITABLE surface the module deliberately exposes.** The wrong way to make one is to change `setpoint`'s type (§822.2); the right way is an additive slot/action (§822.3-4).

## 822.2 — The schema-risk axis: additive = SAFE, retype = LOSSY→OUTAGE `[CERT-doc via B795 + CERT-live B800]`
[B795]'s classifier grades a module change by its effect on an EXISTING `.bog`:
- **`add_slot` (frozen prop / ACTION / topic) = SAFE** (`[B795] §795 table r1`: "old `.bog` has no entry → new default"). Adding `setpointCmd` or `applySetpoint` adds a slot the saved bog simply doesn't reference — a reload re-decodes cleanly, no data loss, no boot risk.
- **RETYPE = LOSSY (complex→simple) or OUTAGE (simple→complex / a frozen owning class)** (`[B795] §795.1`). Retyping `setpoint` `BStatusNumeric`→`BDouble` is the **complex→simple = LOSSY** case, and it is exactly what the live log shows: `WARNING [sys.xml] Cannot set property RoomPanel.setpoint: ClassCastException: BStatusNumeric cannot be cast to BDouble` (`[B800] §800.8` line 102 — the saved value is DROPPED, not merely warned). The **station-crashing** `SEVERE [sys] Cannot load station … ClassCastException` in the same incident (`[B800] §800.8` line 105) was a DIFFERENT co-deployed retype (`BRelTime`→`BComplex`, a frozen owning-class change = OUTAGE) — so "the retype crashed the station" conflates a LOSSY setpoint-drop with a co-deployed OUTAGE. **Cite the two classes separately** (the honest form of the lead's "exit-31/-5" ask):
  - **exit 31** = `build.sh :clean` blocked by a **station lock** on `modules/<jar>` (`[B807]`, `toolbelt/build.sh:15,82-88`) — a BUILD-TIME nuisance (mirror `modules/`), **NOT a data risk**. Do not confuse it with a schema outage.
  - **load-time schema failure** = the `.bog` re-decode: `WARNING [sys.xml] Cannot set property` (LOSSY, value dropped) or `SEVERE [sys] Cannot load station` (OUTAGE, no boot) — the real risk, `[B800] §800.8`.

**Verdict**: any change that keeps `setpoint`'s type is SAFE; any change to its type is at best LOSSY (value silently lost) and, if it touches a frozen owning class, OUTAGE. The additive options are the only safe ones.

## 822.3 — Option A: a `setpointCmd` writable-double slot `[CERT for the oBIX mechanics; INFER for the wiring]`
Add a frozen `double` (`BDouble`) property `setpointCmd`, `Flags.SUMMARY | Flags.OPERATOR` (writable, not readonly); in `changed()`, `if (p == setpointCmd) setSetpoint(BStatusNumeric.make(getSetpointCmd()))` — the command slot drives the existing setpoint internally.
- **oBIX-writable — YES, natively**: a `BDouble` is `BSimple`, so the encoder DOES mark it `writable="true"` under `canWrite` (`ObixUtils.encode:241-243`), and a bare `<real val="21.5"/>` PUT decodes via the SIMPLE path `sink.asSimple().decodeFromString` (`ObixDecoder.java:195/344`) — **no "Cannot translate"**. So the write-server PUTs `/obix/config/…/Cuarto{n}/setpointCmd` with `<real val="21.5"/>`.
- **Schema risk**: SAFE (`add_slot`, §822.2).
- **Permission**: the oBIX login user needs `canWrite` on the slot (the framework `parent.set(…, user)` enforces it; `PermissionException`→`PermissionErr` `ObixUtils.serviceWrite:563`).
- **Caveat ([B816] overlap)**: `setpointCmd` is a SECOND writer of the effective setpoint. If `setpoint` is ALSO link-driven or dashboard-written, the two can fight (last-writer-wins per propagation, [B816] §816.1-2). Make `setpointCmd` the single command source, or gate `changed()` so a link write doesn't ping-pong. This is the cost of a stateful command slot.
- **Audit**: the `changed()` handler can append to `BDashboardService.auditLog` (or rely on the servlet path). Not automatic.

## 822.4 — Option B: an `applySetpoint(BDouble)` OPERATOR action `[CERT]`
Add `@NiagaraAction(flags = Flags.OPERATOR) public void applySetpoint(BDouble v)` on `BRoomPanel`; `doApplySetpoint(BDouble v){ setSetpoint(BStatusNumeric.make(v.getDouble())); }`. A command, not a stored slot — no dual-source-of-truth.
- **oBIX-invokable — YES, natively** (`[CERT]`, the mapper's Q1): every non-hidden, non-topic Action slot renders as an oBIX `<op>` (`ObixEncoder.getKids:512` slot-walk + `encodeOp:477`); a `POST /obix/config/…/Cuarto{n}/applySetpoint` routes `BObixServer.service` POST → `ObixUtils.serviceInvoke:494` → (ordinary Action branch) `dec.decode(a.getParameterDefault())` → `ot.getComponent().invoke(a, val, ot)`. The `BDouble` argument decodes from `<real val="21.5"/>` via `BDouble.decodeFromString` (`ObixDecoder.java:344`). This is DISTINCT from the alarm-ack path ([B671]): ack is a purpose-built `BIObixInvocable` wrapper; an ordinary action goes through `BComponent.invoke`.
- **Permission — the invoke flag [CERT]**: there is NO oBIX-layer `canInvoke` gate in `serviceInvoke`; the enforcement is the framework `BComponent.invoke` checking the action's `OPERATOR_INVOKE`/`ADMIN_INVOKE` against `ot.getUser()`. So `Flags.OPERATOR` on the action + an oBIX login user with operator-invoke = it fires; a read-only user is rejected. (Contrast [B671]: alarm-ack had NO action-permission check because it is not a Baja Action slot.)
- **Schema risk**: SAFE (`add_slot (action)`, §822.2).
- **Audit**: a `BComponent.invoke` goes through the framework action-invocation path (Niagara can log/audit action invokes), and `doApplySetpoint` can also append to `auditLog`. No competing stored slot to reconcile — cleaner than Option A on the [B816] axis.

## 822.5 — Option C: retype `setpoint` to a writable type — REJECTED `[CERT-live]`
Changing `setpoint` from `BStatusNumeric` to `BNumericWritable`/`BDouble` (to expose a priority array or a simple writable) is the change that already failed: LOSSY at best (`[B800] §800.8:102`, the value dropped), and it co-deployed with the boot OUTAGE (`:105`). It also loses the `BStatus` (fault/stale) semantics the dashboard reads ([B821] §821.4 status tags). **Do not retype a persisted slot to gain writability** — add a surface instead.

**Recommendation**: **Option B (`applySetpoint` action)** for an oBIX write-server — it is oBIX-native, schema-SAFE, permission-gated by `OPERATOR_INVOKE`, and has no stateful second slot to reconcile. Option A (`setpointCmd`) is the fallback if the write-server prefers a property PUT over a POST-invoke; watch the [B816] dual-writer overlap. The existing **servlet path** (no code at all, strongest audit) is [B823]'s channel 3 and is the best answer IF the write-server can speak HTTP+CSRF instead of oBIX. Never retype (Option C).
