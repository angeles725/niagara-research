## Run summary

The `reports` focus answered a real client feasibility question from scratch: can the stock Niagara N4 `report`
module deliver a range-scoped PSI report with an Excel-like history table plus an analytics chart marking
alarm-limit crossings? The run inverted its own preliminary thesis. B357 framed the report module as the
central vehicle (spine + grid + exporter). B359 discovered that `BBqlGrid` is a component viewer, not a record
viewer, and that `BHistoryRecord` is a `BStruct` with no `ordInSession` — the table leg is structurally blocked.
B360 found the same `ordInSession` wall for `BAlarmRecord`. B361 found the chart leg blocked at the rt/wb
profile boundary, with alarm bands having no stock API in either path. B362 synthesized: the stock module
contributes only the schedule + delivery wrapper; all three data legs are custom rt-profile code. B363–B365
then confirmed the secondary detail (export formats, ux web layer, wb builder), with B365 issuing a §14
rejection of the delegated sweep's "partially supports history table" reading.

Key method pattern this run: `sonnet` structural sweep per gap (51/57/31/21/14 tool-uses per gap),
then the driver token-verified every load-bearing citation directly before writing the block. Dramatic
negatives in B359 and B361 were each re-measured by two independent methods before entering the block.

## What went well

1. **RE-MEASURE DRAMATIC NEGATIVE (B359 and B361) — hard rule applied both times.** B359 re-measured the
   "BBqlGrid cannot accept history records" finding by (a) the code-path reading (§359.1-2, `null` col-0 →
   NPE) and (b) independently grepping the report module for history-grid classes (`0 files`), and (c)
   checking `BatchResolve`'s fast-path scheme filter (`slot:/virtual:/h:` — `history:` not in the set). B361
   re-measured the "station cannot emit a chart" finding via (a) the `runtimeProfile` entries in three
   `module.xml` files and (b) grepping `report-rt` classes for any chart reference (`0 files`). In both
   blocks the two methods agreed, converting a potentially dramatic single-measurement negative into a
   structural claim with independent corroboration. Exactly the kit's hard rule (PROMPT-LOOP HARD RULES —
   RE-MEASURE A DRAMATIC NEGATIVE).

2. **VERIFY BEFORE ACTING caught a real behavioral over-read in B365.** The R8 delegated sweep saw
   `BComponentGridQueryEditor.isHistoryQuery()` checking whether the query base is `history:`, and
   `?period=` being prepended when it is — and concluded the stock editor "partially supports the history
   table." The driver rejected this on direct re-read of `:750`, which hardcodes `select ordInSession`
   unconditionally. Feeding a history base to that projection is the exact case B359 §359.1-2 proved broken:
   `BHistoryRecord` is a `BStruct` with no `ordInSession` → NPE. The sweep correctly cited the token; its
   capability interpretation was wrong because it lacked the accumulated framework model (the `ordInSession`
   wall from B359). The §14 clarification in B365 §365.3 issued the rejection and corroborated B359 from
   the tooling side. This is the VERIFY BEFORE ACTING + framework-semantic-check pattern applied correctly —
   and it caught a real over-read that would have mislead the §362 composition.

3. **Mid-focus synthesis at 6/9 closed the load-bearing question efficiently.** B362 was written after
   R1/R2/R4/R5/R6/R9 closed (6 gaps), with R3/R7/R8 still open as "secondary detail that does not change the
   composition answer." The synthesis answered the client question fully and framed the remaining three blocks
   as confirmatory. R3 confirmed no native xlsx, R7 confirmed the 3000-row BQL cap + sort disabled, and R8
   confirmed the stock builder hardcodes `select ordInSession` (and issued the §14). None changed the
   composition. Writing the synthesis early once the load-bearing questions are answered — rather than waiting
   for formal exhaustion — is efficient and makes the remaining detail blocks easier to write (they confirm
   the synthesis rather than build toward an unknown conclusion).
