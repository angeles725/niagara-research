# Retro — Improving corpus navigation: connection-graph traversal + semantic search

**Date**: 2026-08-31 · **Scope**: the niagara-research knowledge corpus and its navigation tooling · **Status**: PROPOSE-ONLY (nothing here is applied; each item is a proposal for human review)

**Trigger**: after building `tools/corpus-nav.py`, the operator asked whether navigation could be made *easier* — specifically traversing the connection graph and adding **semantic** ("find by meaning") search — *without* disturbing the vital way we document.

---

## 1. Current state (measured, not assumed)

| Fact | Value | Source |
|---|---|---|
| Blocks | 720 | `corpus-nav.py stats` |
| Synthesis guides (`docs/*.md`) | 12 | stats |
| Retros | 57 | stats |
| Focuses | 55 | stats |
| Blocks with a `## Connections` section | 211 | stats |
| Evidence markers | CERT 12131 · INFER 3259 · CERT-doc 906 · CERT-live 767 · CERT-hw 497 | stats |

**What exists for navigation today:** `CATALOG.md` (autogenerated N↔title index) + `rg` (lexical), Engram `mem_search` (cross-session semantic memory), `module-navigator` (code), `niagara-help` (official Tridium docs), and now `corpus-nav.py` (lexical find/grep, `connections`, `by-marker`, `by-focus`, `stats`).

## 2. The two real gaps

### G1 — The connection graph is real but fragile
211 blocks link to each other, but the references are written **four inconsistent ways**: `[Block N]` (611 occurrences), `[Bloque N]` (13), `[BN]` (8), bare `bloqueN` (5). `corpus-nav.py connections` already normalizes all four with one regex, so traversal *works today* — but it rests on a regex over prose, not on structured data. Any new citation style silently drops edges. **Focus is also not a machine field**: there is no per-block focus attribute; `by-focus` is a heuristic (header `> Focus:` tag on ~71 blocks ∪ RESEARCH-STATE citations).

### G2 — There is no semantic search over the blocks
All block search today is **lexical** (exact substring / regex). "Where did we cover the thing that keeps one unit in defrost at a time" only works if you already know the words in the block. Engram gives semantic recall, but over saved *observations*, not the 720 blocks themselves. This is the single biggest ease-of-use gap.

## 3. Proposals (ranked by value / cost, PROPOSE-ONLY)

### P1 — [HIGH value, LOW cost] Add a local semantic index to `corpus-nav.py`
Add a `semantic <query>` subcommand that ranks blocks by meaning, not words. Keep it **local and optional**:
- Embed each block (H1 + body, chunked) with a small local model; cache vectors in `tools/.corpus-index/` (gitignored). No external service, no network at query time.
- Python is the right language for this (embedding ecosystem lives there — reinforces the earlier "stay in Python, don't switch to Go" decision).
- **Additive**: it indexes the existing blocks as-is. It does NOT change block format, markers, or the authoring flow. Lexical `find`/`grep` stay as the ground-truth fallback.
- Risk: model/dependency footprint. Mitigate by making the semantic index opt-in (a `--build-index` step); if the model is absent, `corpus-nav.py` still runs every lexical command.

### P2 — [HIGH value, LOW cost] Make the connection graph first-class
- **Normalize citations to one canonical form** `[B<N>]` going forward (a lint in `corpus-nav.py`: `lint-refs` flags non-canonical citations; do not mass-rewrite history unless the operator asks).
- **Emit the graph** as an artifact: `corpus-nav.py graph --json` → adjacency list (forward + reverse edges) that other tools (or a future viewer) can consume. Cheap; turns the implicit graph into data.
- Optional: `path <A> <B>` to show how two blocks connect through the graph.

### P3 — [MED value, LOW cost] Make focus a machine field
Add a `> Focus: **<focus>**` header tag to blocks that lack it (only ~71 of 720 have it today), so `by-focus` becomes exact instead of heuristic. Propose-only: this is a bulk edit; do it focus-by-focus at close time, not retroactively in one pass.

### P4 — [MED value] Surface markers + self-verify in search results
Semantic/lexical hits should show the block's evidence posture (CERT vs INFER counts) inline, so a searcher immediately sees how well-grounded a block is. `corpus-nav.py` already parses markers — just fold the tally into `find`/`semantic` output.

## 4. The vital method to PRESERVE (non-negotiable)

Every proposal above is an **index layered over the blocks**, never a replacement. These stay exactly as they are:
- **The block as the unit of truth** — one researched gap per `.md`, H1 + numbered sections + self-verify table + Connections.
- **Evidence markers** ([CERT]/[CERT-doc]/[CERT-hw]/[CERT-live]/[INFER]) and "no citation → no marker".
- **CATALOG.md autogenerated** from H1 (never hand-edited); the three-sources discipline; SOURCES.md registration.
- **Human-readable first**: a new index must never make the corpus require a tool to be read. `rg` and a text editor must keep working with zero infrastructure.

If any semantic/graph layer ever drifts from the blocks, the blocks win and the index is rebuilt.

## 5. Does it help? Verdict

Yes. P1 (semantic) is the highest-leverage ease-of-use win and is additive. P2 (graph as data) makes the 211-block link structure reliable instead of regex-dependent. Both are Python, local, zero-infra, and leave the documentation method untouched. P3/P4 are cheap polish. Recommended order: **P1 → P2 → P3 → P4**, each as a separate reviewed change.
