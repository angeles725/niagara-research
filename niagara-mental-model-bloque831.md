## 831.1 — S21 companion-flag: a class FIELD cleared where the timer is armed, NOT a method-local `[CERT]`
**The lint-timers companion-flag rule (C8, retro campaign8-lint-timers-ext):** a boolean set in the SAME method body as a `Clock.schedule*` must be cleared in `stopped()`/`started()` (a "companion flag" that arms a timer). **The false positive (S21):** the heuristic pairs ANY boolean set near ANY schedule in the file, without requiring (a) the boolean be a class FIELD, or (b) the schedule be in the SAME method body. Evidence at ff1b659 (`BDefrostController.java`): `boolean anyNoHardware = false;` is a **method-LOCAL** (`:718`), declared inside `requestDefrostCycle()` (`:713`) which contains **NO `Clock.schedule`** — the schedules are in OTHER methods (`beginDefrost` etc.: `:808`, `:810`, `:850`, plus `:676/:693` armTrigger, `:877` stagger). A method-local reset to `false` on every call cannot be a companion flag (it has no lifetime past the method), yet the file-scoped heuristic pairs it with the distant schedules → spurious FAIL, which blocks a clean `report-module` on ColdRoomPan-rt. **The precise rule:** flag a companion only when the boolean is a `private`/instance FIELD (grep the field declarations first — `private boolean X` at class scope) AND a `Clock.schedule*` appears in the SAME method body as an assignment `X = true`. A method-local (declared with a type inside a method) is never a companion. `[ev: client BDefrostController.java:713,:718,:808-850 @ ff1b659]` `[ev: retro campaign8-lint-timers-ext]`

## 831.2 — S22 per-slot writing-action: an `@NiagaraAction` BODY writes slot X, scoped to action bodies `[CERT]`
**The ext-writable-shape rule (S19, B823):** a complex `OPERATOR` property (`BStatusNumeric/Boolean/Enum`) that external clients write must have a writing ACTION, else the raw oBIX write to the complex slot hits "Cannot translate"/silent-zero. **The C9 exemption is class-level** (`lint-ext-writable-shape.sh`): a class exposing ANY `@NiagaraAction` is exempt — parity with `module-find.py ext-writable`'s `ok(has-action)`. **The false negative (S22):** the exemption ignores WHICH slot the action writes. Evidence at ff1b659 (`BCompressorControl.java`): `faultReset` is `BStatusBoolean`, `Flags.SUMMARY|OPERATOR`, COMPLEX (`:1612`) — squarely the B823 hazard — and NO `@NiagaraAction` writes it: the class's actions are `tick`/`powerOnExpired` (HIDDEN, `:435/:437`) and `ackAlarm` (`:439`), none touching faultReset. Yet the class-level rule exempts faultReset because those actions exist. **Subtlety the precise rule MUST handle:** faultReset IS written — `setFaultReset(new BStatusBoolean(false))` at `:2025` — but that write is inside the adapter's `execute()`/`changed()` loop (the one-shot auto-clear `if (getFaultReset().getValue()) { ctl.resetFaults(); setFaultReset(false); }`), NOT inside an `@NiagaraAction` body. So a naive "does any method write X" would wrongly exempt it. **The precise rule:** exempt slot X only when the BODY of an `@NiagaraAction` (the method whose annotation names an action, or the `doAckAlarm`-style handler bound to one) contains a write to X — `setX(`, `.set(X,`, or `getX().setValue(`. Reuse S18's slot→writer follow (`lint-silent-protection.sh` Pass-0 dir index) to bind the setter to the slot; SCOPE the search to action-annotated method bodies, excluding `execute()`/`changed()`/generated setters. faultReset then correctly WARNs. `[ev: client BCompressorControl.java:382,:1612,:1626,:2025,:435-447 @ ff1b659]` `[ev: corpus B823]` `[ev: kit lint-ext-writable-shape.sh:14-18]`

## 831.3 — S23 alarm-surface recognition: the two B827 surfaces a lint can match `[CERT]`
**The silent-protection rule (S18, B824):** a protection trip whose only surface is a private field / bare SUMMARY slot with no alarm surface → WARN. Its surface-follow (`lint-silent-protection.sh`) recognises a named `*Alarm/*Fault/…` SUMMARY slot and (post-B827) a child `BAlarmSourceExt`. **The false positive (S23):** it does NOT recognise the PROGRAMMATIC Pattern B surface, so after a component alarms via `BIAlarmSource`/`AlarmSupport.newOffnormalAlarm` the trip is STILL flagged. Evidence at ff1b659: the CP-1 low-suction shed `CompressorControl.java:294` (`if (suctionValid && c.suctionLowLimit > 0d && suction < c.suctionLowLimit) target = Math.min(target, onCount - 1)`) is now alarmed — `BCompressorControl implements BIAlarmSource` (`:447`), `alarm = new AlarmSupport(this, "defaultAlarmClass")` in `started()` (`:1882`), `alarm.newOffnormalAlarm(lowSuctionData(suction))` on the FIRE edge (`:2093`) — yet `lint-silent-protection.sh` on the ff1b659 CompPan-rt tree STILL emits **1 WARN** on that shed (verified 2026-09-06, S23 seeding). **The exact tokens a lint can match (both B827 surfaces):**
- **Pattern A (declarative)** — a child `BAlarmSourceExt` on a point the trip drives: `import javax.baja.alarm.ext.BAlarmSourceExt`, a child point `BBooleanPoint`/`BNumericPoint` (`BEvaporatorUnit.java:193-194` `freezeAlarmPt` type `BBooleanPoint`), `pt.add("…", new BAlarmSourceExt())` in a factory, and a `getXPt().setOut(…freezeTripped…)` drive line — recognised via the field→point→ext chain.
- **Pattern B (programmatic)** — `implements BIAlarmSource` on the class decl (`BCompressorControl.java:447`), `new AlarmSupport(` in `started()` (`:1882`), and `newOffnormalAlarm(` reachable from `execute()` (`:2093`). If ANY of these is present in the class, a trip in that class HAS a tier-1 surface and must not be flagged silent.
**The precise rule:** the surface-follow adds a class-level check — a trip in a class that `implements BIAlarmSource` AND calls `newOffnormalAlarm(` (Pattern B), or that declares a child point carrying a `BAlarmSourceExt` driven from the trip field (Pattern A), is SURFACED. `[ev: client CompressorControl.java:294, BCompressorControl.java:447,:1882,:2093, BEvaporatorUnit.java:193 @ ff1b659]` `[ev: corpus B827 §827.3/§827.4]` `[ev: corpus B824]`

## 831.4 — The shared shape `[INFER, grounded]`
All three are the same defect class: a lint proxy that is TRUE at the wrong granularity — file-scope (S21: any-boolean-near-any-schedule), class-scope (S22: any-action-exempts, S23: no-programmatic-surface-check). Each precise rule narrows to the correct binding — a FIELD armed in the SAME method (S21), an ACTION body that writes THAT slot (S22), a class that raises THAT trip's alarm (S23) — reusing the machinery already in the kit: `lint-silent-protection.sh`'s Pass-0 dir-wide index and slot→writer follow does the field/slot binding for S22 and S23; the paren-balanced multi-line `@Niagara*` join (C8 D9b) parses the annotations. None needs new tooling, only a tighter match. They should ship as one C10 lint-precision PR (or three chained), each with a real-tree pin against ff1b659 (S21: BDefrostController 0 FAIL; S22: faultReset WARNs; S23: CP-1 no WARN). `[ev: kit lint-silent-protection.sh]`
