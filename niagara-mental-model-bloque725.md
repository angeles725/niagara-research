## 1. The two signing worlds (they do not share a cert)

A deployed N4 module jar carries a standard JAR signature block: `META-INF/NIAGARA4.SF` + `META-INF/NIAGARA4.RSA` `[CERT-live]` (same `NIAGARA4` signer base name seen in the SD firmware chain [B676]). But WHICH certificate signs it depends on the path, and there are two independent ones:

- **The gradle build (`com.tridium.niagara-signing` plugin) auto-signs with a PER-MACHINE DEVELOPMENT cert.** Every jar built this session — ColdRoomPan AND the reference `chihuahua-rt/-ux` (both in `build/libs` AND deployed in `<niagara_home>/modules/`) — is signed by `CN=cristian@DESKTOP-4AAQ77H(Niagara4Modules), OU=For Development Purposes Only Do Not Distribute, O=Tridium` (self-signed, valid 1 yr) `[CERT-live]`. This is generated by the plugin's own signer store (`<user_home>/security/signing/`), NOT the Workbench key store.
- **The operator re-signs in Workbench with the real project cert** (`angelessigner`, §3). Re-signing REPLACES the dev signature. This is the intended production step; it is NOT done by gradle.

**Consequence [INFER→CERT-live]:** because gradle ALWAYS re-signs with the dev cert on every build (and the niagara-module plugin auto-copies the jar into `<niagara_home>/modules/`, [module-dev-workflow]), the deployed reference `chihuahua` jars were found carrying the DEV signature, not `angelessigner` — a later build had overwritten the re-signed copy. The Workbench re-sign must therefore be the LAST step, after the final gradle build.

## 2. The user key store — standard JCEKS, but its password is NOT the System Passphrase

`<user_home>/security/keystore.jceks` is a **standard JCEKS** file: magic `CE CE CE CE 00 00 00 02` `[CERT-live]` (`xxd`; identical header on the trust store `cacerts.jceks` and on other installs' key stores). So `keytool -storetype jceks` is the correct type — the command is not the problem.

Yet **no literal password opens it from outside** — every attempt (including the platform admin passwords and the signing-key password) returns `java.io.IOException: Keystore was tampered with, or password was incorrect` `[CERT-live]`. The decisive evidence that the store password is NOT the literal System Passphrase:

- Changing the **System Passphrase** via **Platform Administration → System Passphrase** ("Password change successful") **did NOT modify `keystore.jceks`** — its mtime stayed at the pre-change timestamp `[CERT-live]`.

**Conclusion `[CERT-live]`:** Niagara **manages the key-store password internally** (derived/wrapped under the platform security layer, unlocked only THROUGH Niagara — Workbench Certificate Management opens it with no prompt). The native `keystore.jceks` is therefore **not openable by external `keytool`** by design. This is consistent with the platform-security API surface [B392/B441] where `PlatformSecurityConfigManager.setSystemPassphrase` mediates access. `[INFER]` the exact KDF/wrap is not decoded here (SP-G16, blocked-on-code).

## 3. The project code-signing identity — `angelessigner`

`[CERT]` (Workbench Certificate Management + `keytool`):
- **Alias:** `angelessigner`. **Subject:** `C=MX, ST/L=Chihuahua, O=Alser, OU=Ingnieria, CN=angelessigner`. **Issuer:** `angelessignerCA` (`O=Alser`).
- **Key:** RSA **4096**, sig `SHA256WITHRSA`. **EKU:** Code Signing (`1.3.6.1.5.5.7.3.3`); KeyUsage `digitalSignature`. **Validity:** 2026-05-05 → 2028-05-04.
- **Fingerprints:** SHA1 `90:57:4A:83:8B:67:90:9F:21:A4:A9:26:B4:73:02:7C:BD:FC:66:6D`; SHA-256 (of the entry in the recovered PKCS12) `EB:47:BF:54:4A:4E:A7:BE:30:73:24:2D:86:2E:31:71:D0:31:9B:2F:32:EE:6A:E5:5A:5E:CC:17:83:6B:82:66`.
- **Host-bound CA:** `angelessignerCA` carries an Issuer Alternative Name `otherName oid=tridiumHostId (1.3.6.1.4.1.4131.2) value=Win-6E6E-10AC-D1DD-8276` `[CERT]` — the CA is bound to this host's ID. **Implication `[INFER]`:** for a JACE to ACCEPT a module signed by `angelessigner`, that JACE must trust `angelessignerCA` in its User Trust Store (the B723 trust step); the host-binding scopes where the CA may ISSUE, not where the leaf may be VERIFIED.

The `certManagement/` dir also holds `luissigner`, `sejofa_codesigningcs`, and `default.pem` — multiple dev/OEM signers coexist. `defaultVendor("Angeles")` in the module's `build.gradle.kts` is the module VENDOR string, a SEPARATE concept from the signing cert.

## 4. The Workbench PEM-export AES-GCM gotcha — OpenSSL cannot read it

Exporting `angelessigner` (with private key) from Workbench Certificate Management yields a **PEM** whose blocks are: **1× `ENCRYPTED PRIVATE KEY` + 2× `CERTIFICATE`** (leaf + CA) `[CERT-live]`; a sibling `.p7b` holds only the cert chain (no key).

`openssl pkcs12 -export` on that PEM FAILS — even with the correct password and even with `-provider legacy -provider default` — with:
```
Could not find private key from -in file
error:0300007A ... evp_cipher_asn1_to_param_ex: cipher parameter error
error:0300007A ... PKCS5_v2_PBE_keyivgen_ex: cipher parameter error
```
`openssl asn1parse` of the key block explains it `[CERT-live]`: the encryption is **PBES2 → PBKDF2 (salt 20B, iter 0x0400) → AES-256-GCM** (12-byte IV, 16-byte tag). **OpenSSL's PBES2 decrypt path only supports CBC ciphers, not AEAD/GCM** — hence the "cipher parameter error", regardless of password. `[CERT]` This is a BouncyCastle/Java-produced key (Niagara uses BC, §5); only a GCM-capable stack can read it. (Python `cryptography` does not help — it links OpenSSL for this path, same limit; also not installed here.)

## 5. The recovery — Niagara's own BouncyCastle → PKCS12

Niagara BUNDLES BouncyCastle 1.78.1 (which DOES decrypt PBES2/AES-GCM) at `<niagara_home>/bin/ext/bcstd/` `[CERT-live]`. BC 1.78 is **modularized**: a converter needs **THREE** jars on the classpath, not two —
- `bcprov-jdk18on-1.78.1.jar` (provider), `bcpkix-jdk18on-1.78.1.jar` (PKCS/PEM), and **`bcutil-jdk18on-1.78.1.jar`** — omitting `bcutil` throws `NoClassDefFoundError: org/bouncycastle/asn1/ntt/NTTObjectIdentifiers` (Camellia OIDs `DefaultSecretKeySizeProvider` needs) `[CERT-live]`.

A ~40-line tool `PemToPkcs12.java` (`org.bouncycastle.openssl.PEMParser` → `PKCS8EncryptedPrivateKeyInfo.decryptPrivateKeyInfo(JcePKCSPBEInputDecryptorProviderBuilder…)` → `KeyStore("PKCS12").setKeyEntry(...)`) compiled and ran under Java 8 + the three jars. **Verified output `[CERT-live]`:** `angeles.pfx` = a valid PKCS12 (`keytool -list -storetype pkcs12` → *Keystore type: PKCS12, provider: SunJSSE, 1 entry: `angelessigner, PrivateKeyEntry`*, SHA-256 `EB:47:BF:54…`). A dummy password reaches "Error finalising cipher" (the GCM tag rejecting the wrong key) — proof the classpath is complete and BC decrypts the GCM. Alternative with zero code: re-export directly as **PKCS12/.pfx** from Workbench (avoids the PEM/OpenSSL path entirely).

## 6. The practical how-to (the steps) + the open question

**To sign a module for production (known-good path):** (1) build with gradle (Java-8 + slotomatic; auto-signs with the dev cert); (2) **re-sign the jar in Workbench** Certificate Management with `angelessigner` (LAST — after the final build, §1); (3) ensure the target JACE trusts `angelessignerCA` (User Trust Store, B723).

**To get a portable/CLI-usable signing keystore:** export `angelessigner` from Workbench as PKCS12 directly, OR export PEM and convert with `PemToPkcs12` (§5) → `angeles.pfx`, then `keytool`/`jarsigner`/gradle can consume it.

**OPEN (SP-G16, requires-execution):** whether signing a module with plain `jarsigner` using `angeles.pfx` (signer block named after the alias, not `NIAGARA4`) produces a signature a JACE ACCEPTS as a valid MODULE signature is **UNVERIFIED**. Until tested, Workbench re-sign is the only confirmed path. `[INFER]` the platform likely verifies the chain-to-trusted-CA rather than a fixed block name, but this must be proven on a station.
