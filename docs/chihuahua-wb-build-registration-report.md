### A3. Can THREE parts (rt, ux, wb) of the same `moduleName` coexist?  **[CERT — pattern]**
Yes. This is the normal Niagara multi-part layout; each part is a **separate installable jar**
that shares one `moduleName`. The `jsonToolkit` module proves a ≥2-part layout where the wb
part declares the rt part as a dependency, and Niagara installs them as parts of the same
logical module.

- Generated `jsonToolkit-wb.jar!META-INF/module.xml` (root element):
  ```xml
  <module name="jsonToolkit-wb" ... moduleName="jsonToolkit" runtimeProfile="wb">
  ```
  i.e. the **jar/manifest `name` is `jsonToolkit-wb`** while **`moduleName` is `jsonToolkit`**
  and **`runtimeProfile` is `wb`**. The installer keys parts by `moduleName` + `runtimeProfile`,
  so `chihuahua-rt` / `chihuahua-ux` / `chihuahua-wb` are three distinct rows that reconcile to
  one `chihuahua` module. **[CERT]** (jsonToolkit ships rt+ux+wb jars; see the three
  `jsonToolkit-{rt,ux,wb}.jar` artifacts under `build/libs` and `ORIGINALS-BACKUP/`).
- **Risk / rule:** there can be **at most one part per `(moduleName, runtimeProfile)`** pair.
  Three different profiles never collide. The only conflict risk is two jars claiming the same
  `moduleName`+`runtimeProfile`, which is not your case. **[INFER — low]** confirm no stale
  `chihuahua-wb` from a prior version sits in `!modules` during deploy.

### A4. Profile dependency rules — can `wb` depend on `chihuahua-rt`, `:baja`, `:workbench-wb`, `:bajaui-wb`? Why "rt cannot depend on wb" but "ux depends on rt"?  **[CERT (empirical) + INFER (rule)]**
Yes to all four. The wb part may depend on its own rt part and on rt/ux/wb modules.

- **Empirical [CERT]:** `jsonToolkit-wb.gradle.kts` declares, and the build resolves,
  `api(project(":jsonToolkit-rt"))` (`:85`), `api(":baja")` (`:28`), `api(":workbench-wb")`
  (`:82`), `api(":bajaui-wb")` (`:31`), plus many `*-rt`/`*-ux`/`*-wb` mixed deps (`:25-82`).
  `honeywellSpyderTool-wb.gradle.kts:21-32` does the same (`:baja`, `:bajaui-wb`,
  `:workbench-wb`, `:wiresheet-wb`, multiple `*-rt`). So a wb part depending on rt + wb modules
  is a proven, building configuration under 7.3.40. **[CERT]**
- **The general rule [INFER, well-grounded]:** dependency legality follows **runtime
  availability (profile containment)**, not gradle. A station's class space for a given profile
  only loads parts of that profile *and lower*:
  - `rt` = headless station runtime (no UI). An `rt` part must run on a station with **no
    Workbench and no browser-UX classes present**, therefore `rt` may depend only on `rt`.
  - `ux` = browser/HTML5 tier; a `ux` runtime always has `rt` loaded too, so `ux` may depend on
    `rt` and `ux`. (Your `chihuahua-ux` → `chihuahua-rt` is exactly this.)
  - `wb` = thick Workbench client; a `wb` runtime always has `rt` (and ux assets) available, so
    `wb` may depend on `rt`, `ux`, and `wb`.
  - `se` = a separate "small edition"/special profile, not in the rt⊂ux⊂wb chain.

  Hence **"rt cannot depend on wb"**: an rt-only headless station has no `workbench-wb`/
  `bajaui-wb` classes on its classpath, so an rt part referencing them would `NoClassDefFound`
  at station boot. **"ux depends on rt"** is fine because every ux runtime is a superset of rt.
  This is why your `chihuahua-rt.gradle.kts` notes it *cannot* depend on a `-wb` part.
- **Important nuance [CERT]:** plugin **7.3.40 does NOT enforce these rules at build time** —
  `ModulePart`/the manifest writer contain no profile-compatibility validation (only
  `modulePartName` + `runtimeProfile` round-tripping). The constraint is enforced by the
  **station at install/boot** (class availability). Net: gradle will happily let an rt part
  depend on a wb module; it fails only at runtime. For `chihuahua-wb` this is moot — wb→rt and
  wb→wb are both legal. **[CERT]**

### B4. Is `requiredPermissions="rwi"` valid, and how is it evaluated?  **[CERT]**
Valid. `requiredPermissions` is a per-agent permission-mask string evaluated against the

opened.

- The attribute is real and used natively with mask strings — `"r"` (PropertySheet `:642`),

  = **admin-level**: `r`/`R` read, `w`/`W` write, `i`/`I` invoke. **[CERT — format from

  conservative gate. A user lacking these on the target component will not get the view (or it
  opens read-limited, depending on the host's enforcement point). **[CERT — value valid] /
  [INFER — exact enforcement point (menu hide vs open-deny) confirm at smoke]**

## Block D — `vendorVersion` / `defaultModuleVersion`

### D1. Does adding a NEW wb part require bumping the shared `defaultModuleVersion` (today `1.2`)?  **[INFER — recommend bump]**
Not required for *correctness*, but **recommended** for clean install reconciliation.

Reasoning, grounded in how Niagara reconciles modules vs frozen slots:
- The **frozen-slot compatibility** rule (bump `vendorVersion` when you add a frozen slot to an
  *existing* type so older saved BOGs deserialize correctly) **does not apply here** — you are
  adding a **new type in a new part**, not mutating an existing component's frozen slots. So the
  slot-reconciliation motivation is absent. **[INFER]**
- The remaining reason to bump is **install/redeploy reconciliation**: Niagara compares a
  module part's `vendorVersion` to decide whether to (re)install it. The generated manifests
  share one version across parts (e.g. jsonToolkit's parts all carry one vendorVersion). If you
  ship `chihuahua-wb` at the *same* `1.2` as the already-installed `chihuahua-rt`/`-ux`, the new
  part itself is new (different `runtimeProfile`) so it installs regardless; but bumping (e.g.
  `1.2` → `1.3`) makes the **whole module** visibly change, forces a consistent re-resolve of
  all three parts, and avoids "looks identical, skip" edge cases when redeploying over an
  existing `1.2`. **[INFER]**
- **Recommendation:** bump `defaultModuleVersion` to `1.3` in root `vendor { }` for this
  change. All three parts then publish at `1.3`, keeping `rt`/`ux`/`wb` in lockstep (Niagara
  treats parts of one module as a versioned set). **[INFER — confirm at smoke]**
